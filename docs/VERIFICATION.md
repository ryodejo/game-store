# Итоговая проверка

Дата: 03.10.2026. Окружение: Windows, Temurin JDK 25.0.2, Maven Wrapper 3.3.4 / Maven 3.9.9, PostgreSQL 17.0. Компиляция выполняется с Java release 17.

## Результат

После добавления обязательного email выполнена чистая сборка `mvnw.cmd -B clean verify`, код **0**. XML-отчёты в `target/surefire-reports/` подтверждают **35 тестов, 0 failures, 0 errors, 0 skipped**. Основной JAR обновлён: `target/game-store-1.0.0.jar`; он содержит FlatLaf, прежние зависимости, миграции V1–V5 и все 20 обложек. SMTP, восстановление доступа через email и соответствующая кнопка отменены по запросу пользователя. Полный журнал финальной сборки: `.local-db/email-verify.log`.

Новые проверки отклоняют регистрацию без email, с пустым/пробельным/некорректным адресом через TCP и сервис. PostgreSQL дополнительно запрещает новый аккаунт с NULL email и удаление адреса. Проверены нормализация адреса и вход по email. Переход со старой схемы сохраняет вход аккаунта без email и позволяет добавить адрес с текущим паролем. Существующие проверки аватара, ника, смены пароля, покупок, баланса и прав также проходят. Старое ожидание пустого email в UI-тесте заменено проверкой сохранения исходного обязательного адреса при неправильном текущем пароле.

Миграция V5 применена к рабочей локальной `gamestore`. Контрольные суммы всех строк в users, games, cart_items, orders, order_items, payment_attempts, library и balance_operations до и после совпали. Таблица восстановления не создана. SHA-256 всех 42 файлов legacy совпадает с исходным манифестом; orders.txt не изменён. Отдельная визуальная проверка окон в этом этапе не запускалась; выполнены существующие тесты рендеринга и взаимодействия Swing через TCP.

## Проверенные сценарии

- Регистрация, уникальность логина без учёта регистра, правильный/неправильный пароль, BCrypt-хеш вместо открытого пароля.
- Поиск, жанр, диапазон цены и сортировки; SQL-подобный поисковый ввод не меняет смысл запроса.
- Добавление в корзину без дубликатов, удаление, сумма с сервера.
- Успешная покупка, бесплатная игра, недостаточный баланс, сохранённый отказ и повторная попытка с новым UUID.
- Запрет повторной покупки; одинаковый UUID не списывает баланс повторно и не может относиться к другой игре/пользователю.
- Одновременные одинаковые операции: одно списание. Одновременные разные покупки: баланс не уходит в минус. Одна корзина при конкурентном оформлении имеет одного победителя.
- Искусственная ошибка PostgreSQL после списания, перед записью библиотеки: баланс, корзина, заказы и оплата полностью откатываются; тот же UUID можно безопасно повторить.
- Перезапуск TCP-сервера с новым набором сервисов: пользователь, баланс, библиотека, заказ и результат UUID сохраняются. Корзина также сохраняется между экземплярами сервисов.
- Неавторизованные запросы запрещены; подстановка userId запрещена; чужие детали заказов недоступны, включая административную сессию.
- Обычный пользователь не может читать административный каталог или создавать/изменять игры. Роль проверяется по актуальной записи БД.
- Изменение названия/цены и скрытие игры сохраняют исторические позиции и библиотеку.
- Импорт требует явного сопоставления владельца, не меняет исходный файл, не списывает баланс и не дублирует библиотеку. Ошибочная строка/игра отменяет весь импорт.
- Повреждённые завершённые TCP-сообщения возвращают ошибку и не ломают следующую команду. Слишком большой кадр получает ошибку и закрывает соединение.
- Долгая фоновая задача не блокирует EDT; успешный результат обрабатывается на EDT.
- Экранные действия через TCP: поиск, добавление/удаление из корзины, детали заказа, сохранение административной правки.

Все 20 изображений прочитаны ImageIO из classpath. Снимки работающих экранов получены самим Swing и визуально просмотрены; копии сохранены в `docs/screenshots/`.

Отдельная проверка реальной графической сессии через `DesktopSmoke` завершилась с `DESKTOP_SMOKE_OK` при масштабах FlatLaf **100%, 125%, 150%**. Main из собранного JAR открыл LoginFrame; также показано основное оформление StoreShell в окне 1000×700, после чего тест закрыл созданные окна. Снимки находятся в `target/ui-previews/desktop-100%/`, `desktop-125%/`, `desktop-150%/` и визуально просмотрены. Настройки масштаба Windows не изменялись. Это проверка запуска и оформления окон, а не заявление о ручном прохождении всех сценариев мышью.

UI-интеграционный тест использует реальный TCP-сервер и отдельную схему PostgreSQL. Проверены поиск, состояние корзины, удаление выбранной игры и кнопкой в строке, административное сохранение, исторический снимок названия, детали заказа и пополнение через профиль. Дополнительно проверены сохранение ника и его обновление в навигации, неверный текущий пароль для email и пароля, сохранение нормализованного email, несовпадение новых паролей рядом с полем, предпросмотр аватара без изменения БД, сохранение и удаление аватара. ## БД и сохранность исходников

В `.local-db/data` используется отдельный кластер PostgreSQL с SCRAM-аутентификацией и случайным паролем в игнорируемой локальной конфигурации. Базы — `gamestore` и `gamestore_test`. Миграции V3 и V4 применены к рабочей `gamestore` командой `ServerMain migrate` из собранного JAR. Для каждой миграции сравнение контрольного отпечатка исходных столбцов пользователей и таблиц заказов/позиций, корзины, библиотеки, оплат и пополнений до и после подтвердило полное совпадение. Хеши паролей и содержимое аккаунтов в отчёт не выводились. Существующий системный сервис PostgreSQL и его базы не изменялись.

В начале и конце работы `git status` сообщил, что указанная папка не является Git-репозиторием. Git не инициализировался; коммитов и отправки на GitHub не было.

Исходная версия сохранена в игнорируемой папке `legacy/`: **42 файла**, включая **20 Java-исходников**. SHA-256 каждого резервного файла сопоставлен с манифестом и совпал. `orders.txt` остался на месте; контрольная сумма не изменилась:

## Исправления

В исходной версии пользователи/корзины/история терялись при перезапуске, пароли были открытыми, а сервер доверял userId из TCP-запроса. Покупки использовали double и общую память без защиты от гонок. Оформление корзины могло частично списать баланс, очистить неоплаченные позиции и отправить несколько ответов на одну команду, нарушив порядок последующих ответов клиента. История показывала текущие цены игр вместо цен покупки. Swing выполнял сетевые обращения на EDT, а обложки зависели от рабочей папки.

Эти проблемы устранены серверной БД, сессиями, параметризованными запросами, BCrypt, BigDecimal/NUMERIC, блокировками и едиными транзакциями, идемпотентными UUID, снимками позиций, одним ответом на запрос, ресурсами classpath и SwingWorker-задачами.

## Что осталось

Блокирующих проблем окружения после итоговой проверки нет. Maven был загружен локально, установленный PostgreSQL использован для отдельного кластера. Ограниченная оболочка запрещала PowerShell-сценарии; успешная итоговая проверка выполнена вне неё, без изменения глобальной политики выполнения.

Оригинальный orders.txt **не импортирован в произвольный аккаунт**: владелец должен сначала зарегистрировать новый логин и явно сопоставить его со старым userId через команду импорта из README. Старые логины, даты и исторические цены отсутствуют в файле и не могут быть достоверно восстановлены.

Пределы учебного проекта описаны в README: нет реальных платежей, скачивания, TLS, восстановления пароля и пагинации больших выборок. UUID незавершённого запроса сохраняется в открытом клиенте; после полного закрытия клиента следует проверить историю/библиотеку. Серверная идемпотентность сохраняется в БД.

Точные команды настройки, запуска, назначения администратора, импорта и повторения тестов приведены в [README](../README.md).

## Проверка разграничения src и legacy

Maven явно использует только `src/main/java` и `src/test/java`. Чистая сборка javac обработала 34 текущих исходника и 11 файлов тестов/вспомогательных проверок; файлов legacy среди входных файлов нет. Настройки исключения legacy в VS Code сохранены.

Добавлена `.vscode/settings.json`: Maven-импорт включён, пути src заданы для резервного режима без импортированного Maven-проекта, legacy исключена из Java-импорта и обновления ресурсов Java Language Server. Ассоциация `.java` внутри legacy с plaintext предотвращает Java-диагностику при открытии резервных файлов. Настройки Java/Maven проверены по схемам установленных расширений redhat.java и vscode-maven. Настройки пользователя вне проекта не менялись; сам интерфейс Problems в запущенном VS Code не проверялся. Если остались кешированные сообщения, следует выполнить `Java: Clean Java Language Server Workspace`.

В текущем src воспроизведён настоящий логический дефект: повторное добавление уже имеющейся игры в корзину из 100 игр ошибочно отклонялось проверкой лимита. Новый регрессионный тест сначала завершился с этим отказом, затем успешно прошёл после исправления. Теперь повторное добавление не меняет корзину, а добавление 101-й новой игры по-прежнему запрещено. Ошибок компиляции текущих исходников не обнаружено.

Замечания о double для денег, старых командах BUY/GET_GAMES, доверии к переданному userId и неверной проверке BUY_SUCCESS относятся к резервной версии legacy. Она не участвует в текущей сборке. Все 42 резервных файла повторно проверены по исходному SHA-256-манифесту и не изменены.

Обычный `clean verify` первоначально не дошёл до компиляции: Windows не разрешила удалить основной `target/game-store-1.0.0.jar`. Это отдельная проблема доступа к файлу, не ошибка Java и не ошибка legacy. Для проверки использован чистый каталог `target/verification`, без остановки чужих процессов. Параметр `gamestore.build.directory` позволяет выбирать каталог сборки; по умолчанию остаётся `target`. Позже проверка эксклюзивного чтения основного JAR прошла, и обычный `package` успешно обновил его. Стандартные команды запуска из README используют уже исправленную версию. Конкретный процесс, первоначально блокировавший файл, не установлен.
